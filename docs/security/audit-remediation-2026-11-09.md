# 2026-11-09 audit remediation

This change addresses the code and repository-workflow findings CHAP-001 through CHAP-027 from the full application audit. It was integrated over main commit `2cb17528625b0bd7bdd64d829361a1b59a5c5456`, preserving concurrent release, metadata, Windows migration, packaging and publication-gate changes. An independently dispatched v0.9.995 release has since passed its publication gate; this audit did not dispatch it or deploy a production instance.

The 26 application and repository-workflow findings are implemented. **CHAP-021 is a separate repository-administration proposal and has not been applied.** Main remains unprotected. The prepared `security/main-branch-protection.json` is a proposal, not an active GitHub rule.

## Operator-visible behavior

- On a fresh local-authentication installation, enter username `setup` and the password from AppData's `setup-token` file when the browser prompts. Create the normal account immediately. Unix permissions are owner-only; Windows inherits the existing AppData ACL. Keep that directory private. Existing configured SSO does not enter this path.
- UI credentials are intentionally short-lived. A background tab refreshes on visibility; a restarted app or changed authentication settings require a new UI credential. Authenticated UI requests refresh immediately after a 401 and retry once; live-update reconnection also refreshes before retrying. Logged-out sessions still require login. Calendar URLs generated by the UI now contain a stable read-only feed credential, including legacy Readarr feed compatibility. It cannot call the API or mint another credential; rotating the master API key revokes these subscriptions. Regenerate old calendar links to replace their full-scope API keys. Existing external API integrations continue to use their configured API keys.
- Public cover/download/update fetches reject private, loopback, reserved and cloud-metadata destinations at connection time. Configured non-direct proxy paths fail closed for these public fetches because they cannot prove the destination socket policy. Local download clients remain a separate trusted integration path.
- JavaScript-based download resolution needs Linux, a non-root application account, bubblewrap, user namespaces and the packaged Chromium version. No unsandboxed fallback is available. Windows, macOS and other unsupported hosts can still use ordinary HTTP resolution. Ubuntu 24.04 can require an administrator-approved AppArmor profile for user namespaces (see [Ubuntu's documentation](https://documentation.ubuntu.com/security/security-features/privilege-restriction/apparmor/#apparmor-unprivileged-user-namespace-restrictions)); the application does not disable that host policy. Browser acceptance uses Ubuntu 22.04, which supports the required namespaces without changing system-wide AppArmor settings.
- Archives permit at most 20,000 entries and 30 minutes of extraction. Media permits 16 GiB per entry / 128 GiB total; backups 32 / 64 GiB; updates 2 / 4 GiB. HTTP update downloads are limited to 2 GiB and 15 minutes. These are explicit safety ceilings rather than unbounded inputs.
- A pending full restore applies on the next service/interactive startup. Recovery directories ending in `.failed-*` preserve failed attempts for operator inspection. A restore does not commit merely because SQLite opens; application startup must complete.
- Automatic updates reject old releases without the new attestation bundle. Standard Linux/macOS/Windows packages bundle GitHub CLI 2.103.3. FreeBSD must install a native `gh` with attestation support; absence or verification failure blocks the update. Upgrading from an older installation without these protections requires a separately trusted initial installation.
- Kubernetes defaults now request 100m CPU/256 MiB and limit 4 CPU/4 GiB. Operators should size these values for their library and conversion workload. Root is used only for the documented container permission bootstrap before the application drops privileges.

## PostgreSQL, recovery and provenance controls

The `PostgreSQL acceptance` workflow runs disposable PostgreSQL 16 and 17 services on main pushes. The expanded smoke and evidence gate also run in release validation. Every PostgreSQL fixture is selected: database inspection/selection, legacy conversion, real dump/restore, quality-profile lifecycle, and atomic repository operations. Results are rejected if empty, skipped, failed, missing a required family or inconsistent. XML evidence parsing rejects DTD/entity payloads and oversized reports; its parser dependency is hash-pinned. Shared SQLite/PostgreSQL transaction cases cover commit, outer rollback, nested rollback/abandonment, and constraint failures with suppressed events.

`Native audit acceptance` builds retained current-source archives, verifies their source SHA and checksums against pinned predecessor archives, and runs installed migration/recovery on matching Linux, macOS and Windows hosts. `Media recovery acceptance` uses the pinned real-tool image and the complete native application with read-only candidate inputs. Evidence is retained separately from component test results.

Update verification binds the requested filename and SHA-256 to the **same signed subject**. Release archive jobs and final publication execute the updater's cryptographic trust policy, requiring all ten archive bundles and the exact release version, source commit, filename and digest. Missing or incompatible bundles block publication. The earlier v0.9.990 predates this remediation and has no signed update bundles; the hardened updater correctly refuses it. The independently initiated v0.9.995 publication passed verification for all ten signed archives. An installed end-to-end update from a previous version is a separate acceptance check.

## Verification queue disposition and limits

The original queue distinguishes additional acceptance work from confirmed vulnerabilities:

- V01: fresh-instance authentication and real sandboxed browser behavior now have hosted runtime evidence, in addition to the routing, ownership, socket and scope regression fixtures. This is not an exhaustive penetration test of every deployment/authentication combination.
- V02: the supplied [#198 release titles](https://github.com/snapetech-org/chaptarrng/issues/198) are covered by `ReleaseTitleMatchSpecificationFixture`; [#180's Project Hail Mary subtitle equivalence](https://github.com/snapetech-org/chaptarrng/issues/180) and parody/illustrated-edition negatives are covered by `TrackedDownloadSameRecordingFixture`.
- V03: configured-provider metadata search requested by [closed issue #133](https://github.com/snapetech-org/chaptarrng/issues/133) is present in `BookInfoProxy.SearchForNewEntity`.
- V04: restored dependency graphs receive advisory scans and a retained SBOM. Extended EPUB/image/audio fuzz campaigns and scans of every operator-installed image remain separate assurance work; no such campaign is claimed here.
- V05: live PostgreSQL, synthetic whole-application media recovery and native installed migration/rollback results are recorded above. The v0.9.995 Linux x86 installed migration/rollback gate also passed; FreeBSD native installation and rollback still need their own host acceptance. Operator-populated snapshots and complete acquisition/Seerr fulfillment require their own data and service inputs.
- V06: the 47 webpack warnings are CSS-order warnings. Production builds and current frontend contracts pass; no runtime defect is established merely by the warnings. They have not been suppressed. Forced dependency resolutions remain verified by the locked build and dependency scan.
- V07: deployment-specific mounts, reverse-proxy behavior, historical secret exposure and credential rotation require the actual deployment. Repository tests and scans do not establish those external states.
- V08: the Cloudron candidate permits only the literal WebSocket Upgrade protocol and removes h2c.

The published v0.9.995 release passed positive signature verification and installed migration/rollback on the eight standard runtimes plus Linux x86. Those results do not establish FreeBSD installed acceptance, a previous-to-current automatic update in a running installation, production cutover or representative operator-data acceptance. Publication remains behind the existing fail-closed gates.

Semgrep's pinned rule set contains 1,074 Community Edition rules; parsing limitations for some C#/shell constructs, raw Helm templates and PowerShell workflow subpatterns remain. Trivy separately renders/scans the chart. Rules are privately materialized from immutable upstream sources; they are not redistributed in this repository. Nineteen reviewed deployment exceptions remain path-specific, justified and expire on 2026-12-31; they do not suppress dependency or secret findings. No scan is a guarantee that every vulnerability or credential format is absent.
